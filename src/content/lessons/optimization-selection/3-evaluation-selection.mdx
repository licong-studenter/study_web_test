"这个算法更好"是一句没有信息量的话。更好在哪里？在什么场景、什么硬件、什么预算下更好？算法选型需要把模糊偏好变成可测量、可复现的证据。

## 1. 先定义任务与约束

评估之前必须写清楚：

- 输入分布：光照、地形、速度、障碍密度。
- 成功标准：到达目标、保持平衡、误差阈值、完成时间。
- 安全边界：最大速度、最小距离、允许的失败方式。
- 资源预算：CPU/GPU、内存、功耗、通信带宽。
- 部署条件：是否需要嵌入式、是否可联网、是否可人工接管。

若成功标准只写"效果良好"，不同人会用不同方式解读，实验结果无法比较。

## 2. 多指标矩阵

一个实用矩阵可以包含：

| 指标 | 度量方式 | 关注点 |
| --- | --- | --- |
| 精度 | 误差、成功率、IoU、跟踪 RMSE | 任务完成质量 |
| 实时性 | 平均/尾部延迟、控制周期超时率 | 是否可部署 |
| 鲁棒性 | 扰动、遮挡、地形变化下性能下降 | 边界稳定性 |
| 可解释性 | 失败是否可定位、约束是否可检查 | 维护与审计 |
| 实现成本 | 代码量、依赖、调参时间 | 团队可承担性 |
| 能耗 | 每次决策的功率/能量 | 续航与散热 |

这些指标经常冲突。更高精度可能意味着更大模型与更高延迟；更强鲁棒性可能需要更多传感器与更复杂的状态估计。选型不是寻找单项冠军，而是寻找满足约束的帕累托折中。

## 3. 平均值会骗人

平均成功率 90% 可能来自"简单场景全成功、困难场景全失败"，也可能来自"所有场景都九成成功"。这两种系统风险完全不同。

至少应报告：

- 分层结果：按场景难度、速度、光照分组。
- 尾部指标：最差 5% 延迟、最大跟踪误差。
- 失败类型：碰撞、超时、发散、通信丢失。
- 置信区间：样本量不足时不要只报一个点估计。

对安全关键系统，失败模式比平均性能更重要。一个从不对行人让行的算法，即使平均路径很短，也不能部署。

## 4. 回归实验设计

回归实验的目标是回答："这次改动是否破坏了已有能力？" 基本流程：

1. 固定代码版本、配置、随机种子与硬件。
2. 运行一组覆盖核心场景的基准。
3. 记录指标、日志、视频与失败原因。
4. 与基线做统计比较，而不只是看单个样本。
5. 对显著变化做根因分析。

```python
def summarize(runs):
    success = sum(run["success"] for run in runs) / len(runs)
    p95 = sorted(run["latency_ms"] for run in runs)[int(0.95 * len(runs))]
    failures = {}
    for run in runs:
        if not run["success"]:
            failures[run["reason"]] = failures.get(run["reason"], 0) + 1
    return {"success": success, "p95_latency_ms": p95, "failures": failures}
```

这段代码展示"成功率 + 尾部延迟 + 失败分布"的最小组合。真实报告还应包含版本、配置与数据哈希。

## 5. 从离线指标到在线风险

离线 benchmark 只覆盖有限场景。部署前还需要：

- 仿真中的压力测试与对抗场景。
- 真机低速、空载、受控环境验证。
- 通信中断、传感器失效与急停测试。
- 人工接管与降级策略演练。

在线监控同样重要。部署后要记录延迟、误差、约束违反与人工接管次数，用真实运行数据更新评估。

<Callout type="safety">
不要用"平均结果更好"覆盖"少数场景更危险"的事实。安全评估必须单独列出最坏情况与不可接受失败，而不是把它们平均掉。
</Callout>

## 6. 一页选型结论

最终选型文档应包含：

- 问题与约束。
- 候选算法与版本。
- 评估矩阵与权重。
- 关键实验与统计结果。
- 失败模式与降级方案。
- 采用理由与已知风险。

这页文档比一张漂亮的可视化更有价值，因为它让后来者知道为什么选、何时该换、换的时候要验证什么。

## 本节小结

- 算法选型必须先定义任务、成功标准与资源约束。
- 多指标矩阵能揭示精度、实时性、鲁棒性与成本之间的冲突。
- 平均值会掩盖分层差异与尾部风险。
- 回归实验要固定版本、种子与配置，并记录失败分布。
- 安全关键系统必须单独评估最坏情况与降级策略。
