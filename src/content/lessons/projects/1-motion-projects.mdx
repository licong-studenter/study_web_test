运动控制项目的代码量往往不大，但横跨实时控制、通信、配置与状态管理。直接读某个算法文件，容易看到公式却不知道它在系统中的位置；从入口开始，才能理解“什么时候调用、输入从哪里来、输出到哪里去”。

本节以 MotionSDK 与 Lite3_rl_deploy 为例，练习同一套拆解方法。

## 1. 四步拆解法

### 1.1 找入口

从 `main`、launch 文件或启动脚本开始，列出：

- 程序启动后创建了哪些对象。
- 读取了哪些配置文件。
- 启动了哪些线程 / 节点。
- 进入哪个初始状态。

### 1.2 画状态机

机器人运动通常有明确状态：初始化、站立、阻尼、行走、故障。状态机决定“当前允许什么指令”。很多“指令无效”的问题，其实是系统没有进入正确状态。

### 1.3 追数据流

沿一条指令追踪：

```text
速度指令 → 步态规划 → 足端轨迹 → 逆运动学
        → 关节目标 → 通信 → 驱动器 → 传感器反馈
```

再沿一条状态流追踪：

```text
IMU / 编码器 / 足端接触 → 状态估计 → 控制器 → 日志 / 可视化
```

两条流在控制器处汇合。把它们的频率、单位与坐标系标出来，就能发现大部分接口问题。

### 1.4 找失效处理

关注超时、断连、越界、传感器异常与急停路径。一个项目是否成熟，往往体现在异常路径，而不是正常路径。

## 2. MotionSDK：传统控制链路

`Lite3_MotionSDK` 是 Lite3 运动主机上的控制开发包，包含控制接口、通信示例与 MPC 实现。阅读时建议关注：

| 模块 | 需要回答的问题 |
| --- | --- |
| 通信 | 与感知主机 / App 如何交换数据？ |
| 状态机 | 有哪些运动状态？如何切换？ |
| 步态 | 相位、占空比、步幅如何生成？ |
| MPC | 预测模型、代价函数、约束与求解频率？ |
| 安全 | 哪些条件会触发停止或阻尼？ |

官方 README 同时提示：新项目可以优先关注 `rl_training` 与 `Lite3_rl_deploy` 这条强化学习路线。MotionSDK 仍然是理解传统控制与工程结构的良好样本。

## 3. Lite3_rl_deploy：学习策略链路

`Lite3_rl_deploy` 把训练好的策略部署到仿真或真机。其链路大致为：

```text
ONNX 策略 → 观测构造 → 推理 → 动作缩放
          → PD 目标 / 力矩 → 通信 → 机器人
```

README 中的仿真构建示例：

```bash
mkdir build && cd build
cmake .. -DBUILD_PLATFORM=x86 -DBUILD_SIM=ON -DSEND_REMOTE=OFF
make -j
```

真机部署需要把平台改为 ARM、关闭仿真，并配置网络地址与端口。README 提供了 MuJoCo 与 PyBullet 两种 sim-to-sim 仿真器，以及键盘 / 手柄控制示例。

阅读时重点关注：

- 观测向量的构造顺序与归一化。
- 动作如何映射到关节目标。
- 控制频率与推理频率是否一致。
- 状态机如何从站立切换到 RL 控制。
- 策略失效时是否有安全兜底。

## 4. 两条链路的比较

| 维度 | MotionSDK / MPC | Lite3_rl_deploy / RL |
| --- | --- | --- |
| 核心知识 | 动力学、优化、控制 | 强化学习、仿真、策略部署 |
| 可解释性 | 较高 | 较低 |
| 复杂地形泛化 | 依赖建模与调参 | 依赖训练分布与随机化 |
| 实时计算 | 在线优化，计算量可控 | 推理快，训练成本高 |
| 调试重点 | 约束、模型、参数 | 观测、奖励、接口一致性 |
| 安全兜底 | 易于设计解析约束 | 需要额外安全层 |

两条链路并不互斥。实际系统常用 MPC 或 VMC 作为底层安全控制，用学习策略处理复杂地形，或在策略失效时切换到传统控制器。

## 5. 经典训练框架

如果希望深入强化学习训练本身，可以阅读：

- `leggedrobotics/legged_gym`：ETH 的经典四足训练环境，适合理解环境组织与奖励设计。
- `leggedrobotics/rsl_rl`：轻量 PPO 实现，适合理解策略、价值网络与训练循环。

阅读这些框架时，不要只看网络结构。环境步进、观测构造、终止条件与奖励计算，往往比网络层数更影响结果。

## 6. 一份阅读计划

建议用一周时间完成：

| 天 | 任务 | 产出 |
| --- | --- | --- |
| 1 | 读 README、目录与依赖 | 仓库地图 |
| 2 | 找入口、画状态机 | 状态转换图 |
| 3 | 追一条速度指令 | 数据流图 |
| 4 | 追一条状态反馈 | 频率与坐标系表 |
| 5 | 找异常与安全路径 | 失效清单 |
| 6 | 跑通仿真示例 | 运行日志 |
| 7 | 写一页总结 | 可分享的工程笔记 |

> 工程提示：读代码时随手记录“未理解的问题”，而不是停下来逐行死磕。先建立全局地图，再回头解决关键疑问，效率更高。

## 7. 一条完整的调用链实例

以“速度指令让机器人向前走”为例，可以把调用链写成：

```text
/cmd_vel
  → 速度限幅与超时检查
  → 步态相位更新
  → 足端轨迹生成
  → 逆运动学
  → 关节目标 / 力矩
  → UDP 发送
  → 运动主机执行
  → /joint_states 与 IMU 反馈
```

每一步都应能回答三个问题：输入是什么、输出是什么、失败时怎么办。例如逆运动学失败时，是保持上一帧、降低步幅还是进入保护状态？超时检查是在桥接节点做，还是在运动主机做？这些决定会直接影响系统安全性。

## 8. 代码阅读的产出

阅读代码不应只留下“看过了”的印象。建议产出四类文档：

- **仓库地图**：目录、依赖、启动方式。
- **状态机图**：状态、事件、转移条件。
- **数据流图**：话题、频率、坐标系。
- **风险清单**：超时、断连、限幅、急停路径。

一页纸的总结，比几十页逐行注释更容易被团队复用。

## 本节小结

- 运动控制项目应从入口、状态机、数据流与失效路径四个层面拆解。
- MotionSDK 代表传统 MPC 链路，Lite3_rl_deploy 代表学习策略部署链路。
- 两条链路的调试重点不同，但都需要安全兜底与接口一致性。
- 一份有产出的阅读计划，比漫无目的地浏览代码更有效。
