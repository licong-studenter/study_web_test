感知与导航项目的代码往往比运动控制更分散：视觉节点、SLAM、地图服务、规划器、控制器、行为树、任务脚本分别运行在不同进程。把它们串起来，比单独写好一个检测模型难得多。

本节选择三类项目，练习同一种系统视角：谁提供输入、谁消费输出、坐标系如何连接、失败如何传播。

## 1. 视觉交互：Deepdog_Lite3

`StarsJXB/Deepdog_Lite3` 是一个集二维码识别、语音播报与运动控制于一体的四足机器人实验案例。其闭环大致为：

```text
相机 → 二维码检测 → 解码 / 业务逻辑
                    ├──> 语音播报
                    └──> 运动指令 / 动作反馈
```

这类项目的技术难点不在单个模型，而在状态管理：

- 识别到二维码后，机器人应该停下、转向还是继续？
- 播报期间是否允许接受新指令？
- 重复识别同一二维码时如何避免反复触发？
- 识别失败或误识别时如何恢复？

建议用显式状态机管理交互流程，并为每个动作设置超时与取消条件。

## 2. 自主导航：sdk_deploy + Nav2

`DeepRoboticsLab/sdk_deploy` 面向 Deep Robotics 机器人的 sim-to-sim 与 sim-to-real 部署，README 提到支持 M20 与 Lite3。`syswonder/robot-deep_robotics-lite3` 则提供了 Lite3 相关的系统脚本与部署参考。

ROS 2 Nav2 的典型模块：

| 模块 | 职责 | 关键输入 |
| --- | --- | --- |
| 地图服务 | 发布静态地图 | 地图文件、坐标系 |
| 定位 | 估计机器人在地图中的位姿 | 激光 / 视觉、里程计 |
| 代价地图 | 表达障碍与通行代价 | 点云、地图、膨胀参数 |
| 全局规划 | 计算从起点到目标的路径 | 地图、目标点 |
| 局部控制 | 跟踪路径并避障 | 局部代价地图、速度 |
| 行为树 | 组织导航任务与恢复行为 | 目标、状态、事件 |

完整链路：

```text
传感器 → SLAM / 定位 → 地图 → 全局规划
                              ↓
                        局部代价地图
                              ↓
                        局部控制器 → /cmd_vel
                              ↓
                        运动主机 → 机器人
```

集成时最常见的问题：

- 地图坐标系与里程计坐标系不一致。
- 定位跳变导致路径频繁重规划。
- 代价地图膨胀过大，窄通道不可通行。
- 局部控制器速度上限与机器人能力不匹配。
- 恢复行为（清空代价地图、旋转、后退）未测试。

## 3. 边缘检测：YOLO + TensorRT

竞赛与巡检项目常使用 YOLO 系列模型做目标检测，并通过 TensorRT 部署到边缘设备。典型优化链路：

```text
PyTorch 模型 → ONNX → TensorRT engine
              → 预处理 / 后处理
              → 检测结果 → 业务逻辑
```

部署时要验证：

- 输入尺寸、颜色通道与归一化是否一致。
- NMS 阈值与类别映射是否正确。
- FP16 / INT8 量化后的精度变化。
- 端到端延迟与帧率。
- 不同光照、遮挡与运动模糊下的表现。

检测结果必须与机器人坐标系对齐，否则“看到目标”不等于“知道目标在哪”。

## 4. 项目拆解模板

面对任意感知 / 导航项目，可以用以下模板：

| 问题 | 记录内容 |
| --- | --- |
| 输入是什么 | 传感器、话题、频率、坐标系 |
| 输出是什么 | 地图、位姿、目标、速度指令 |
| 谁消费输出 | 规划器、控制器、任务层 |
| 时间尺度 | 感知频率、规划频率、控制频率 |
| 失效模式 | 遮挡、丢帧、定位跳变、网络断连 |
| 安全兜底 | 降速、停车、恢复行为、人工接管 |

这张表能快速暴露“模块都写了，但系统不工作”的原因。

## 5. 仿真到真机的集成差异

| 维度 | 仿真 | 真机 |
| --- | --- | --- |
| 传感器 | 理想或简化噪声 | 标定误差、遮挡、抖动 |
| 时间 | 可暂停、可重放 | 实时、不可回退 |
| 网络 | 本机回环 | 延迟、丢包、带宽限制 |
| 地图 | 可完美对齐 | 动态物体、地图漂移 |
| 安全 | 重置即可 | 碰撞与损坏不可逆 |

因此，真机集成应逐步增加复杂度：先静态定位，再低速导航，再加动态障碍，最后做完整任务。

> 工程提示：为导航系统保留“人工接管”与“安全停车”入口。自动导航失败时，系统应能明确报告失败原因，而不是无限重试。

## 6. Nav2 参数与失败模式

Nav2 的行为高度依赖参数。常见的参数族包括：

- 代价地图的分辨率、膨胀半径与障碍物层。
- 全局规划器的搜索策略与代价函数。
- 局部控制器的速度、加速度与跟踪容差。
- 恢复行为的触发条件与顺序。

参数不是越保守越安全。膨胀半径过大、速度过低，可能让机器人在狭窄空间里永远无法完成任务；反过来，过度激进会放大定位误差与碰撞风险。应在仿真中建立一组典型场景，用成功率与完成时间共同评价参数。

恢复行为也需要测试。机器人卡住时，系统可能尝试清空代价地图、旋转、后退或重新规划。如果恢复行为没有超时或次数限制，可能陷入无限循环。

## 7. 项目集成检查表

- 地图坐标系与里程计坐标系是否一致。
- 定位更新频率是否满足控制器要求。
- 代价地图是否包含动态障碍。
- 局部控制器速度上限是否与机器人能力匹配。
- 恢复行为是否有次数与时间上限。
- 人工接管与安全停车是否可用。
- 任务失败时是否记录原因与现场数据。

这份检查表比“能跑通一次”更能说明系统是否可交付。

## 本节小结

- 视觉交互项目的核心是状态管理与触发条件，而不是单个模型。
- Nav2 导航链路需要地图、定位、代价地图、规划、控制与行为树协同。
- 边缘部署要验证预处理、量化、后处理与坐标系对齐。
- 项目拆解模板能帮助定位集成问题，仿真到真机应逐步增加复杂度。
