训练曲线漂亮，不等于策略可以部署。部署是另一套问题：模型如何在目标硬件上运行？输入从哪里来？输出如何变成关节指令？延迟多大？出错时如何安全停下？

最便宜的失败场所是 sim-to-sim。把策略放进另一个物理引擎，能暴露它对某一个仿真器参数的过拟合；最贵的失败场所是真机，所以必须在部署前把接口、时延与安全逻辑逐项验证。

## 1. ONNX 导出

ONNX 提供跨框架的推理格式。导出时要确认：

- 输入维度与顺序：例如观测向量长度、关节顺序、是否包含历史帧。
- 输出维度与含义：关节目标偏移、力矩或速度。
- 归一化：均值 / 方差是否已固化进模型，还是在外部处理。
- 动态维度：是否需要批量推理；部署通常固定 batch=1。
- 算子兼容性：目标推理引擎是否支持所有算子。

一个概念性的导出检查：

```python
import onnxruntime as ort

session = ort.InferenceSession("policy.onnx")
for item in session.get_inputs():
    print("input", item.name, item.shape, item.type)
for item in session.get_outputs():
    print("output", item.name, item.shape, item.type)
```

导出后必须用同一组观测对比 PyTorch 与 ONNX 的输出。若误差超过阈值，先检查 dtype、归一化与算子，而不是直接上机器人。

## 2. sim-to-sim 验证

`Lite3_rl_deploy` 提供了 MuJoCo 与 PyBullet 的 sim-to-sim 部署示例。根据其 README，典型编译流程为：

```bash
mkdir build && cd build
cmake .. -DBUILD_PLATFORM=x86 -DBUILD_SIM=ON -DSEND_REMOTE=OFF
make -j
```

随后在一个终端启动仿真器，在另一个终端运行部署程序：

```bash
# 终端 1
cd interface/robot/simulation
python3 mujoco_simulation.py

# 终端 2
cd build
./rl_deploy
```

README 中给出的键盘控制包括站立、进入 RL 控制、趴下、阻尼模式与前后左右移动。具体按键以当前仓库为准。

sim-to-sim 检查清单：

1. 观测顺序、单位与归一化是否一致。
2. 控制频率与动作缩放是否一致。
3. 关节零点与方向是否一致。
4. 策略输出是否被正确映射到 PD 目标或力矩。
5. 在平坦、斜坡、扰动与不同初始姿态下是否稳定。
6. 失败时是否能回到安全状态。

## 3. 真机部署

真机部署需要处理三类额外问题：

### 3.1 硬件与构建

运动主机通常是 ARM 架构，需要把 `BUILD_PLATFORM` 切换为对应平台，并关闭仿真开关。交叉编译或本机编译时，要确认依赖库、CMake 版本与运行时库一致。

### 3.2 通信

README 中的网络配置示例包含运动主机地址与端口。不同设备与网络环境的地址可能不同，必须以现场配置为准。部署前应验证：

- 主机与机器人网络连通。
- 端口未被防火墙拦截。
- 心跳 / 状态消息持续更新。
- 断连后系统能进入安全状态。

### 3.3 时延

| 环节 | 典型量级 | 风险 |
| --- | --- | --- |
| 传感器采样 | 1–20 ms | 时间戳不准 |
| 状态估计 | 2–20 ms | 滤波延迟 |
| 策略推理 | 1–10 ms | 输入预处理开销 |
| 通信 | 1–20 ms | 抖动、丢包 |
| 关节执行 | 1–5 ms | 驱动器响应 |

端到端延迟会压缩控制裕度。训练时若没有模拟延迟，策略在真机上可能表现为振荡或反应迟钝。

## 4. 状态机与安全兜底

一个可部署的系统通常包含状态机：

```text
IDLE ──> STAND ──> RL_READY ──> RL_RUN
  ↑         │           │           │
  └─────────┴───────────┴──> FAULT / DAMPING
```

每个状态都要定义：

- 进入条件与退出条件。
- 允许的指令范围。
- 超时与异常处理。
- 人工急停后的行为。

RL 策略应始终运行在安全壳内：速度限制、姿态限制、关节限位、通信超时与电流保护。策略负责“怎么走”，安全层负责“什么时候必须停”。

## 5. 部署后的评估

部署不是终点。应持续记录：

- 任务成功率与失败类型。
- 端到端延迟与丢帧率。
- 关节跟踪误差与峰值力矩。
- 电池电压、温度与降额事件。
- 不同地面、负载与操作者下的表现。

把这些数据回流到训练与随机化范围，形成闭环。一次成功的演示只是样本，长期稳定性才是系统能力。

> 安全提示：首次真机运行强化学习策略时，使用低速、低增益、物理防护与人员监护。不要在人群、楼梯或湿滑地面直接测试未经验证的策略。

## 6. 延迟预算与状态机案例

假设策略推理耗时 6 ms，通信 8 ms，状态估计 5 ms，传感器采样 10 ms，驱动器响应 3 ms。端到端延迟约 32 ms，看起来不大，但如果控制周期是 20 ms，策略实际上在控制两个周期之前的世界。

部署前应做一次延迟测量：在输入端打时间戳，在关节指令发出前再打一次，统计均值、95 分位与最大值。若延迟抖动很大，策略需要更保守的动作或额外的预测补偿。

状态机应明确以下转移：

```text
IDLE → STAND：关节使能、姿态就绪
STAND → RL_RUN：策略加载、观测有效、安全区确认
RL_RUN → FAULT：超时、姿态越界、通信丢失
FAULT → DAMPING：关闭力矩、记录日志
```

每个转移都要有可观测的日志。否则出现“机器人突然不动”时，无法判断是策略、通信还是安全层触发。

## 7. 部署回滚

每次部署新策略，都应保留上一版模型、配置与启动脚本。回滚流程应经过测试：

1. 停止当前控制，进入阻尼或支撑状态。
2. 切换模型与配置版本。
3. 重新执行健康检查。
4. 低速验证站立与直行。
5. 记录回滚原因与结果。

没有回滚能力的升级，会让一次失败变成长时间停机。把回滚当作常规操作，而不是紧急救援。

## 8. 部署检查表

- [ ] ONNX 输入输出与训练时一致。
- [ ] 归一化与动作缩放一致。
- [ ] sim-to-sim 在多种地形与扰动下通过。
- [ ] 控制频率与延迟满足要求。
- [ ] 状态机与安全兜底可触发。
- [ ] 回滚版本可用。
- [ ] 日志记录观测、动作、延迟与异常。
- [ ] 真机测试有人员监护与物理防护。

部署不是“把模型拷过去运行”，而是一条需要验证、监控与回滚的工程流程。

## 本节小结

- ONNX 导出后必须检查输入输出、归一化与数值一致性。
- sim-to-sim 是部署前最便宜的失败场所，应覆盖多种地形与扰动。
- 真机部署的关键是接口对齐、通信可靠、时延可控与安全兜底。
- 部署后的数据回流，决定策略能否持续改进。
