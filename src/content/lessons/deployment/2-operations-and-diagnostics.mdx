系统出问题时，最危险的不是故障本身，而是你不知道发生了什么。没有日志、指标与健康检查，排查只能依赖现场观察和猜测；有了它们，很多问题可以在造成损失前被发现。

运维的目标不是“永不出错”，而是“快速发现、快速定位、快速恢复”。

## 1. 最小可观测性方案

### 1.1 日志

日志应包含时间、来源、级别、消息与上下文。机器人系统常见的日志来源：

- 应用日志：控制、感知、导航节点。
- 系统日志：`journalctl`、内核消息、驱动。
- ROS 2 日志：节点启动、参数、异常。
- 仿真日志：物理参数、随机种子、回合结果。

日志不应记录密钥、密码或完整个人信息。对高频数据，使用采样或聚合，而不是把每一帧都写入磁盘。

### 1.2 指标

最小指标集：

| 类别 | 指标 |
| --- | --- |
| 通信 | 话题频率、丢包率、端到端延迟 |
| 计算 | CPU / GPU / 内存 / 温度 |
| 运动 | 关节跟踪误差、姿态、速度 |
| 供电 | 电压、电流、剩余电量 |
| 感知 | 帧率、检测数量、地图更新 |
| 任务 | 成功率、失败类型、完成时间 |

### 1.3 健康检查

为关键模块提供健康状态：

```text
/health/motion   OK | DEGRADED | FAULT
/health/perception OK | DEGRADED | FAULT
/health/network  OK | DEGRADED | FAULT
```

上层可以根据健康状态降速、切换模式或安全停止。健康检查不应只返回“进程还活着”，还要检查数据是否新鲜、频率是否正常、误差是否在范围内。

## 2. 故障树

以“机器人突然停止响应速度指令”为例，可以建立故障树：

```text
速度指令无效
├── 上游未发布
│   ├── 导航节点崩溃
│   └── 任务状态机未进入运行态
├── 通信中断
│   ├── 网络断开 / IP 变化
│   ├── 端口被防火墙拦截
│   └── UDP 丢包严重
├── 运动主机拒绝指令
│   ├── 未使能 / 处于阻尼模式
│   ├── 安全限制触发
│   └── 电池低电量保护
└── 执行层异常
    ├── 关节过流 / 过热
    └── 控制器进入故障状态
```

故障树把“猜”变成“逐项排除”。每一项都应有对应的检查命令或日志字段。

## 3. 常见故障与排查

| 现象 | 可能原因 | 排查 |
| --- | --- | --- |
| 话题频率为 0 | 节点未启动、QoS 不匹配 | `ros2 node list`、`ros2 topic info` |
| 数据跳变 | 时间戳错乱、解析错误 | 检查时间源与消息定义 |
| 定位漂移 | 外参、同步、打滑 | 检查 TF、标定与里程计 |
| 关节抖动 | 增益过高、延迟、噪声 | 降低增益、检查频率与滤波 |
| 突然降额 | 过热、低电量、过流 | 查看温度、电压与驱动器日志 |
| 网络断连 | IP 冲突、Wi-Fi 抖动、防火墙 | `ping`、`ip addr`、端口测试 |

## 4. 电池与热管理

电池是四足机器人最容易被忽视的约束之一：

- 避免深度放电，设置低电量告警与自动停止阈值。
- 长期存放时保持适宜电量与温度。
- 记录充放电循环与内阻变化。
- 飞行 / 运输前确认电池状态与固定方式。
- 发现鼓包、异常发热或电压骤降时立即停用。

热管理同样重要。计算平台与电机驱动器过热会触发降频或降额，表现为性能突然下降。应为长时间任务设计散热与休息策略。

## 5. 固件与升级

固件升级应遵循：

1. 阅读发布说明与兼容性要求。
2. 备份当前配置与标定。
3. 在受控环境中升级一台设备。
4. 执行回归测试：通信、传感器、站立、低速运动。
5. 确认无误后再批量升级。

不要在生产任务前临时升级。升级与任务之间应留出验证窗口。

> 工程提示：为每次故障建立一条“故障卡片”：现象、复现步骤、根因、修复、预防措施。故障库会逐渐成为团队最有价值的资产。

## 6. 日志分析案例

假设现场反馈“机器人偶尔向左偏”。日志中可能看到：

- 左前关节跟踪误差逐渐增大。
- 左侧足端接触时间变短。
- 电池电压在加速时明显下降。
- 左前电机温度高于其他关节。

单看任何一条都不足以定因。把它们放在同一时间轴上，可能发现：电压下降导致左前电机扭矩不足，足端接触变差，身体向左倾，控制器增大补偿，最终表现为偏航。

日志分析的关键是时间对齐。把控制指令、关节状态、IMU、电压与温度放在同一时间基准下，才能看到因果关系。

## 7. 故障演练

定期演练比事后总结更有效。可以设计一组低风险故障：

- 拔掉一个非关键传感器。
- 临时阻断一个话题。
- 修改错误的外参。
- 让电池进入低电量告警。
- 触发急停并复位。

每次演练记录发现时间、定位时间、恢复时间与根因。长期积累后，团队会形成一套可复用的故障库。

## 8. 值班与交接

长时间任务需要明确的值班与交接机制。交接内容至少包括：

- 当前系统状态与未解决问题。
- 最近一次升级与回滚记录。
- 电池、温度与网络异常。
- 已执行的测试与剩余风险。

交接不是“口头说一句没问题”，而是让对方能独立判断系统是否适合继续运行。把交接清单写进运行手册，可以显著降低人为失误。

## 本节小结

- 最小可观测性包括日志、指标与健康检查。
- 故障树能把模糊现象拆成可验证的排查项。
- 电池与热管理会直接改变系统性能与安全边界。
- 固件升级必须经过备份、单机验证与回归测试。
