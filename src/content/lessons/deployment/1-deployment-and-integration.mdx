实验室里常见的交付方式是：工程师把电脑接到机器人上，输入一串历史命令，系统跑起来了，大家鼓掌。两周后换一个人来操作，系统却怎么都起不来——因为环境、配置、脚本顺序都只存在于某个人的终端历史里。

可交付系统必须能被他人在没有口头指导的情况下复现。这需要需求、版本、步骤、验收与回滚都被明确记录。

## 1. 从需求到方案

部署前先回答五个问题：

1. **任务是什么**：巡检、跟随、搬运还是教学演示？
2. **环境是什么**：室内 / 户外、地面材质、光照、网络覆盖。
3. **边界是什么**：速度、负载、续航、工作空间、人员安全。
4. **失败怎么办**：能否急停、能否远程接管、能否安全趴下。
5. **如何验收**：用哪些指标判断“完成”。

需求不清会导致技术选型反复。一个“在园区巡检”的需求，可能同时包含定位精度、续航、避障、数据回传与夜间作业，必须拆成可验证的子项。

## 2. 版本固化

机器人系统是软件、硬件、模型与配置的集合。建议维护一份版本清单：

| 类别 | 记录内容 |
| --- | --- |
| 操作系统 | 发行版、内核版本、镜像哈希 |
| 运行时 | ROS 2、Python、CUDA、TensorRT |
| 代码 | 仓库、commit、子模块版本 |
| 模型 | 训练配置、权重哈希、ONNX 版本 |
| 固件 | 运动主机、驱动器、传感器固件 |
| 配置 | 网络、标定、增益、限速 |
| 硬件 | 本体批次、传感器型号、安装位置 |

这份清单应与发布包一起归档。没有它，故障排查只能靠猜。

## 3. 双主机安装

双主机系统的安装顺序建议为：

1. **运动主机**：操作系统、驱动、运动控制程序、网络配置、固件。
2. **感知主机**：操作系统、ROS 2、感知 / 导航依赖、模型与配置。
3. **网络**：地址、端口、路由、防火墙、时间同步。
4. **外设**：相机、激光雷达、IMU 的驱动与标定。
5. **启动脚本**：统一的启动、健康检查与日志目录。

安装过程中应避免“边装边改”的混乱。每完成一步，记录验证命令与预期输出。例如：

```bash
# 网络连通性
ping -c 3 <motion-host>

# 关键话题频率
ros2 topic hz /joint_states
ros2 topic hz /imu/data

# 系统资源
top -b -n 1 | head -20
```

## 4. 分阶段联调

不要一次性启动所有模块。推荐按以下阶段推进：

| 阶段 | 目标 | 通过条件 |
| --- | --- | --- |
| 单机自检 | 主机、驱动、传感器正常 | 所有设备可枚举，数据稳定 |
| 通信联调 | 双主机话题互通 | 关键话题频率与延迟达标 |
| 静态控制 | 站立、关节模式切换 | 姿态稳定，急停有效 |
| 低速运动 | 直行、转向、停止 | 跟踪误差在阈值内 |
| 感知闭环 | 建图、定位、避障 | 地图一致，避障成功 |
| 任务演练 | 完整任务流程 | 成功率与安全指标达标 |

每个阶段都要有明确的通过条件与回滚方式。失败时回到上一阶段，而不是在整机联调中同时排查所有问题。

## 5. 验收与回滚

验收指标应与任务绑定，例如：

- 定位误差、建图一致性。
- 速度跟踪误差、姿态误差。
- 任务成功率、平均完成时间。
- 通信丢包率、端到端延迟。
- 电池续航、温升、故障恢复时间。

回滚方案同样重要：保留上一个可用版本、配置与模型，确保出现问题时能快速恢复到已知状态。没有回滚能力的升级，是一次高风险赌博。

> 工程提示：把启动、停止、健康检查与日志收集写成脚本，而不是依赖终端历史。交付时，脚本本身就是文档的一部分。

## 6. 部署脚本与启动顺序

可交付系统应提供统一入口，而不是让操作者记住十几条命令。一个最小启动脚本可以包含：

```bash
#!/usr/bin/env bash
set -euo pipefail

LOG_DIR="${LOG_DIR:-$HOME/lite_logs/$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$LOG_DIR"

source /opt/ros/humble/setup.bash
source "$HOME/lite_ws/install/setup.bash"

ros2 launch lite_bringup motion.launch.py 2>&1 | tee "$LOG_DIR/motion.log"
```

启动顺序应显式：先启动底层通信与状态发布，再启动感知，最后启动任务层。每一步都要有健康检查；前一步未就绪时，后一步不应盲目启动。

## 7. 一次验收的组织方式

验收不应由开发者自己“演示一遍”就结束。建议由未参与开发的人按文档执行：

1. 从零启动系统，记录耗时与失败步骤。
2. 执行健康检查与急停测试。
3. 完成低速直行、转向与停止。
4. 执行感知与导航任务。
5. 注入一个故障，观察系统是否安全降级。

文档中未写清、需要口头解释的步骤，都应补回文档。能被他人在没有开发者陪同的情况下复现，才算真正交付。

## 8. 交付包结构

一个可交付的发布包通常包含：

```text
release/
├── app/             # 程序与依赖
├── config/          # 网络、标定、控制参数
├── models/          # 策略与模型文件
├── scripts/         # 启动、停止、自检
├── docs/            # 运行手册与故障库
└── manifest.json    # 版本、哈希、兼容性
```

`manifest.json` 应记录每个组件的版本与校验值。发布时生成，部署前校验。这样即使目录被替换或文件损坏，也能在启动前发现问题。

## 本节小结

- 部署从需求与边界开始，而不是从敲命令开始。
- 版本固化覆盖操作系统、代码、模型、固件与配置。
- 双主机安装应按“单机—网络—静态—低速—闭环—任务”分阶段联调。
- 验收指标与回滚方案是交付的一部分。
